# Phase 4: Search behavior

> **Status**: STUB. Expand when Phase 3 is done. The biggest design
> question — what memory representation to use — should be resolved
> with experiments during Phase 3 prompt engineering.

## Goal

Turn the single-step VLM into a real search agent. The robot can be
dropped in a room without the target visible, given a task, and
*actively search* until it finds the target (or concludes it can't).
This is what makes the demo land — viewers should see the robot
*looking around* and *deciding where to go*, not just executing
hardcoded patterns.

## Non-goals

- No multi-room navigation with doorway reasoning (out of scope).
- No SLAM or persistent maps. Memory is short-term, per-task.
- No fine-tuning still.
- No multi-robot coordination — that's the SortBots framing, not this
  project's deliverable.

## Deliverables (rough)

1. Memory layer in `crawler_vlm`:
   - Text-based memory log of decisions and observations.
   - Passed to the VLM each step, alongside the current frame.
   - Bounded in length (most recent N entries, or summarized).
2. Search loop logic:
   - Detect when target is visible → switch to "approach" mode.
   - Approach mode: visual servoing-lite, drive toward target until
     ultrasonic stops the robot.
   - Confirmation: require 2 consecutive frames of "target_visible:
     true" before committing to approach (anti-hallucination).
3. Termination logic:
   - "Target found" — robot stops, reports location in natural language.
   - "Cannot find" — robot stops after N steps or T minutes, reports
     what it tried.
   - "Stuck" — robot detects it's in a loop (revisiting same spots),
     reports.
4. Operator output:
   - Final report generated by the VLM in natural language: "Blue book
     located near the bookshelf, north side of room."
   - Logged to file + printed to console + optionally TTS.
5. Updated prompts in `prompts/`:
   - `search_step.txt` — main search-loop prompt.
   - `approach_step.txt` — approach mode prompt.
   - `final_report.txt` — generates the natural-language report.

## Design notes (to be expanded)

- **Memory representation**: text log is the lightest option and works
  well with the VLM's reading. Spatial representation (an occupancy
  grid, a list of "places visited") is more sophisticated but probably
  not necessary for room-scale search.
- **Anti-hallucination**: the VLM will sometimes claim to see the target
  when it doesn't. Two-frame confirmation is the simplest mitigation.
  Could also have a separate verification step that re-prompts with
  "are you SURE you see the target?"
- **Loop detection**: track headings and rough motion; if the robot has
  been "exploring" for >2 minutes in the same orientation cluster, flag
  as stuck.
- **Approach mode is a state, not a free decision.** Once committed,
  the VLM stops getting full search prompts and gets a simpler
  "approach the target" prompt until ultrasonic stops the robot or
  the target leaves the frame for >2 seconds (then back to search).

## Open questions

- How long is the memory window? 10 steps? 30? Tune via bag replay.
- Does the memory get summarized periodically, or just truncated? Start
  with truncation, add summarization if needed.
- Should the VLM see ultrasonic readings too, or is the camera enough?
  Probably include — it's cheap context.
- How does the operator know the search succeeded? Just terminal output,
  or something flashier (audio cue, photo of target sent)?

## Working style

Heavy bag-replay iteration. The hardware tests are slow and unreliable.
Build up a library of search scenarios (5-10 bags from different rooms,
different targets) and iterate the prompts against them.

For each prompt change:
1. Replay 5 scenarios.
2. Compare action sequences against previous version.
3. Decide if it's better, worse, or sideways.
4. Commit the prompt change with a short note in `prompts/CHANGELOG.md`.

Hardware runs only after replay-tests are solid.

## Testing plan

- **Bag replay**: 5+ recorded scenarios with different target visibility
  states. Manually review action sequences for sensibility.
- **Loop detection test**: deliberately give an impossible task ("find
  the unicorn") and verify the robot terminates with "cannot find"
  rather than wandering forever.
- **Hardware**:
  - Setup A: target visible at start. Robot should approach directly.
  - Setup B: target out of view, requires turning. Robot should turn,
    find, approach.
  - Setup C: target out of view, requires moving to a new spot. Robot
    should explore, find, approach.
  - Setup D: target not present. Robot should give up gracefully.
  - Each setup, 3 runs. Track success rate.

## Scope

Large. The biggest phase. Plan a multi-week effort. Prompt engineering
is the bottleneck, not code.

## Definition of done

- Robot can solve at least Setups A, B, C in a familiar room with ≥60%
  success rate across 3 runs each.
- Setup D terminates with a sensible "cannot find" message within 2
  minutes.
- The behavior is *visually recognizable as searching* to a non-expert
  watching the demo video.
